# 마음의 문 출시 준비 10회 개선 보고서

대상은 공개 미리보기 저장소 `jh4334/fabletest2-memento-preview`의 `169f88da0ceb09597c02c21c8d9e52039e3fe675` 이후 코드다. 원본 `jh4334/fabletest2`는 읽기 전용 `upstream`으로만 확인했으며, 수정·push·PR·Pages 설정 변경을 하지 않았다.

## 1회차 — 서버 오류 때 마지막 정상 게임으로 복구

1. 개발자 검토: 서비스워커의 core 자산 경로가 네트워크 우선이지만 HTTP 503도 정상 응답처럼 반환했다.
2. 코드리뷰:
   - 버그 가능성: 서버가 응답만 하면 캐시 폴백이 실행되지 않았다.
   - 구조·유지보수성: 성공 응답 저장과 오류 폴백의 경계가 응답 상태를 표현하지 못했다.
   - 성능: 새 요청이나 재시도는 추가하지 않는 것이 적절했다.
   - 보안: 외부 origin이나 새 캐시 권한은 필요하지 않았다.
   - 예외 처리: Promise rejection만 처리하고 HTTP 오류를 빠뜨렸다.
3. 사용자 검토: 혼란은 흰 화면에 원인이 보이지 않는 점, 흐름 실패는 시작 화면까지 못 가는 점, 실패 상황은 일시적 503이었다. 모바일·데스크톱 모두 같은 서비스워커 경로였고, 재시도 대기 없이 마지막 정상 캐시를 즉시 여는 편이 체감 속도에도 유리했다.
4. 우선순위: P0. core 응답이 성공 범위가 아닐 때 기존 정상 캐시를 사용한다.
5. 실제 반영: `sw.js`, `tools/swtest.js`, `tools/browsertest.js`를 수정했다. RED 0/1 뒤 unit GREEN, 실제 Chromium에서 503 대신 캐시된 `game.js` 200을 확인했다.
6. 결과: 커밋 `8039d67`. 서버 장애 복구는 해결했고, 첫 설치의 선택 자산 실패는 다음 회차로 분리했다.

## 2회차 — 선택 아이콘 실패가 PWA 설치를 막지 않게 함

1. 개발자 검토: core shell과 홈 화면 아이콘이 하나의 `cache.addAll`에 묶여 있었다.
2. 코드리뷰:
   - 버그 가능성: 아이콘 404 하나가 전체 install promise를 거부했다.
   - 구조: 부팅 필수 자산과 설치 장식 자산의 실패 정책이 같았다.
   - 성능: 개별 optional write는 설치 때만 발생해 영향이 작다.
   - 보안: 기존 자산 allowlist를 그대로 유지했다.
   - 유지보수성·예외 처리: core는 fail-fast, optional은 settled라는 규칙을 코드로 드러냈다.
3. 사용자 검토: 아이콘 하나 때문에 게임 전체가 설치되지 않는 이유를 사용자가 이해하기 어렵고, 첫 실행·재실행 흐름이 함께 막혔다. 모바일 홈 화면과 데스크톱 설치형 PWA 모두 실패할 수 있었으며, 매번 온라인 셸을 다시 받는 체감 지연도 생겼다.
4. 우선순위: P0. core 설치는 엄격하게, 선택 아이콘은 best-effort로 분리한다.
5. 실제 반영: `sw.js`, SW/브라우저 테스트를 수정했다. 아이콘 404를 주입한 첫 설치 뒤 controller 활성화와 오프라인 재진입을 확인했다.
6. 결과: 커밋 `4b9f324`. PWA 기본 사용은 아이콘 상태와 분리됐고, core 누락은 계속 설치 실패로 남겨 안전성을 유지했다.

## 3회차 — 삭제 안전망 실패 시 세이브 원본 보존

1. 개발자 검토: 슬롯 삭제 전에 만드는 되돌리기 스냅샷 저장 실패를 무시하고 실제 키를 삭제했다.
2. 코드리뷰:
   - 버그 가능성: 저장 공간 부족·사생활 모드에서 복구 불가능한 삭제가 가능했다.
   - 구조: 삭제 전제조건의 성공 여부가 호출자에게 전달되지 않았다.
   - 성능: 삭제 전 단일 snapshot write만 유지했다.
   - 보안: 학생 데이터 범위를 늘리지 않고 기존 localStorage 키만 다뤘다.
   - 유지보수성·예외 처리: `deleteSlot`의 boolean 결과를 제목 흐름까지 연결했다.
3. 사용자 검토: 확인 뒤 성공 효과가 나와 삭제가 안전하게 끝났다고 오해하기 쉬웠고, 실패 뒤 복구 흐름도 없었다. 공용 모바일·데스크톱 기기의 사생활 모드나 용량 부족에서 진행이 사라질 수 있었으며, 응답 지연보다 데이터 손실 방지가 우선이었다.
4. 우선순위: P0. snapshot이 durable하지 않으면 어떤 save/learning key도 지우지 않는다.
5. 실제 반영: `src/game.js`, 슬롯·브라우저 테스트를 수정했다. write throw 주입 뒤 슬롯·학습 기록 보존, 경고 표시, 삭제음 억제를 확인했다.
6. 결과: 커밋 `2a8e5bb`. 삭제는 원자적 전제조건을 갖게 됐고, 복원 중간 실패는 다음 회차에서 별도 처리했다.

## 4회차 — 백업 복원을 전부 성공하거나 전부 되돌리게 함

1. 개발자 검토: 백업 key를 차례로 쓰다가 하나가 실패해도 성공처럼 반환하고 앞선 새 값은 남겼다.
2. 코드리뷰:
   - 버그 가능성: 옛 세이브와 새 학습 기록이 섞인 부분 복원 상태가 생겼다.
   - 구조: 허용 key 검사만 있고 값 형식·transaction 경계가 없었다.
   - 성능: 최대 세 슬롯의 작은 localStorage preimage만 추가했다.
   - 보안: allowlist 밖 key는 계속 거부하고 non-string 값도 쓰기 전에 거부했다.
   - 유지보수성·예외 처리: durable undo, write, rollback, cache invalidation의 결과를 구분했다.
3. 사용자 검토: “복원 완료” 뒤 일부만 바뀌어 무엇을 믿어야 할지 헷갈리고, 실패에서 원래 상태로 돌아갈 흐름도 없었다. 모바일·데스크톱의 같은 파일 가져오기 경계에서 발생하며, 약간의 사전 스냅샷 비용보다 일관된 학생 데이터가 중요했다.
4. 우선순위: P0. 모든 입력을 먼저 검증하고 첫 write 실패에 모든 touched key를 이전 상태로 복구한다.
5. 실제 반영: `src/game.js`, smoke/브라우저 테스트를 수정했다. 실제 파일 선택 흐름과 중간 write throw에서 old data 전체 보존과 실패 화면을 확인했다.
6. 결과: 커밋 `176f37f`. 백업 복원이 원자적으로 바뀌었고, 저장 실패를 조용히 삼키는 다른 학습 경로는 다음 회차로 남겼다.

## 5회차 — 학습 기록 저장 실패를 사용자에게 알림

1. 개발자 검토: 정답 통계·도전·일지·사전사후 등 여러 writer가 localStorage 오류를 빈 catch로 끝냈다.
2. 코드리뷰:
   - 버그 가능성: 화면상 성취와 실제 저장 상태가 달라졌다.
   - 구조: 이미 있는 `noteStorageFail` 경계가 일부 writer에서만 사용됐다.
   - 성능: 실패 때 상태와 notice만 바꾸며 정상 write 비용은 늘지 않는다.
   - 보안: 오류 상세나 저장 내용을 화면·로그에 노출하지 않았다.
   - 유지보수성·예외 처리: 의미 있는 진척 write 실패를 하나의 지속 경고로 통일했다.
3. 사용자 검토: 학생은 기록 성공으로, 교사는 보고서 완성으로 오해했고 실패 후 백업으로 이동할 단서가 없었다. 모바일·데스크톱 모두 같은 저장소를 사용하며, 플레이를 멈추거나 느리게 하지 않고 지속 경고만 보여 주는 흐름이 필요했다.
4. 우선순위: P1. 플레이는 계속하되 저장 불가 상태를 시각·aria-live로 지속 표시한다.
5. 실제 반영: `src/game.js`, 슬롯·브라우저 테스트를 수정했다. prototype write fault 뒤 `storageOk=false`와 사용자 경고를 확인했다.
6. 결과: 커밋 `d125fbc`. 실패가 더는 조용하지 않으며, 입력 lifecycle 결함은 다음 회차로 분리했다.

## 6회차 — 앱 전환·터치 취소 뒤 고착 입력 해제

1. 개발자 검토: element의 `touchend/touchcancel`만 믿어 전역 취소나 visibility loss 때 held state가 남았다.
2. 코드리뷰:
   - 버그 가능성: 캐릭터 자동 이동·A 버튼 고착이 가능했다.
   - 구조: 키보드, 스틱, 버튼 소유권 해제가 여러 handler에 흩어졌다.
   - 성능: blur/cancel/hidden 같은 저빈도 lifecycle에서만 O(입력 수) 초기화한다.
   - 보안: 이벤트 범위와 수동 입력만 다루며 새 권한은 없다.
   - 유지보수성·예외 처리: 한 `releaseAllInputs`가 pressed/held/touch ID/knob/repeat를 함께 초기화한다.
3. 사용자 검토: 모바일에서 앱 전환 뒤 캐릭터가 혼자 움직이면 조작법을 헷갈리고 진행을 되돌려야 했다. 데스크톱 blur도 같은 실패 경계였으며, 복귀 즉시 입력을 비우면 추가 대기나 느린 재초기화 없이 정상 흐름으로 돌아간다.
4. 우선순위: P1. blur, global touchcancel, hidden에서 동일 release boundary를 호출한다.
5. 실제 반영: `src/game.js`, 브라우저 테스트를 수정했다. RED 2건 뒤 글로벌 cancel과 hidden 모두 입력·스틱 시각 상태가 초기화됨을 확인했다.
6. 결과: 커밋 `215295e`. 기존 멀티터치 5개 동작을 유지하면서 interruption 고착을 제거했다. 잔여 문제는 실제 iOS WebKit의 시스템 제스처 조합을 로컬 자동화에서 확인하지 못한 점이다.

## 7회차 — 터치 동작을 키보드·보조기기에서도 사용 가능하게 함

1. 개발자 검토: `div role=button` 다섯 개는 기본 tab 순서와 Enter/Space 동작이 없었다.
2. 코드리뷰:
   - 버그 가능성: 전역 key listener를 쓰지 못하는 보조 입력에서 동작 불가였다.
   - 구조: 브라우저가 제공하는 native button 의미를 수동으로 흉내 내고 있었다.
   - 성능: click handler 다섯 개의 비용은 무시 가능하다.
   - 보안: 입력 이벤트만 변경했고 HTML injection 경로는 없다.
   - 유지보수성·예외 처리: native activation을 재사용하고 pointer click 중복만 `detail`로 차단했다.
3. 사용자 검토: 키보드·스위치 사용자는 버튼을 찾고도 누르는 흐름을 이해할 수 없었고, 모바일 터치만 가능한 것처럼 보였다. 데스크톱 Tab/Enter/Space와 모바일 터치를 같은 행동으로 연결했으며, 별도 지연이나 이중 입력 없이 즉시 반응해야 했다.
4. 우선순위: P1. 기존 CSS·터치 동작은 유지하면서 요소를 `button type=button`으로 바꾼다.
5. 실제 반영: `index.html`, `src/game.js`, 브라우저 테스트를 수정했다. 다섯 native button, A focus, Enter·Space 이름 화면 진입을 확인했다.
6. 결과: 커밋 `c88da38`. touch와 assistive activation이 하나의 행동을 공유하고 중복 발화하지 않는다. 잔여 문제는 Canvas 본문 전체가 여전히 기존 aria-live 미러에 의존한다는 점이다.

## 8회차 — 엔딩 대기 화면의 다음 행동을 즉시 설명

1. 개발자 검토: anti-skip 시간 전에는 진행 문구가 없고, aria-live와 모바일 A label도 상태를 반영하지 않았다.
2. 코드리뷰:
   - 버그 가능성: 사용자가 멈춘 화면으로 오해하고 반복 입력하거나 종료할 수 있었다.
   - 구조: 같은 threshold가 입력·그리기·접근성에 따로 표현됐다.
   - 성능: frame마다 이미 계산하던 단순 상태다.
   - 보안: 해당 없음. 새 외부 입력이나 저장 경계가 없다.
   - 유지보수성·예외 처리: 한 ending readiness 상태를 canvas, aria-live, touch label이 공유한다.
3. 사용자 검토: 네 엔딩 모두 “왜 안 넘어가지?”라는 혼란과 반복 입력 흐름이 있었고, 모바일 A는 계속 `결정`으로 보여 실패처럼 느껴졌다. 데스크톱·모바일·스크린리더에 같은 준비 상태를 즉시 알려 체감 대기를 설명했다.
4. 우선순위: P1. guard는 유지하되 대기 중 `잠시만`, 준비 후 `마을로`를 즉시 안내한다.
5. 실제 반영: `src/game.js`, 브라우저 테스트를 수정했다. 네 엔딩의 대기/준비 aria-live, canvas 복귀 문구, 모바일 label을 확인했다.
6. 결과: 커밋 `ac11f02`. 엔딩을 급히 건너뛰지 않게 하면서도 화면이 멈춘 듯한 인상을 없앴다. 잔여 문제는 의도적인 anti-skip 대기 자체는 유지되어 매우 빠른 재플레이 사용자에게 짧은 대기로 남는다는 점이다.

## 9회차 — 긴 교사용 진단 리포트를 끝까지 탐색

1. 개발자 검토: 모든 논리 행을 y=92부터 그려 viewport 아래 내용이 잘렸고 스크롤·페이지 입력이 없었다.
2. 코드리뷰:
   - 버그 가능성: 긴 추천과 하단 통계가 영구적으로 보이지 않았다.
   - 구조: 표시 layout과 export text를 구분할 필요가 있었다.
   - 성능: 실제 font measure 결과를 보고서 상태에서 재사용해 매 프레임 재계산을 줄였다.
   - 보안: local-only report이며 export 범위나 데이터 수집을 늘리지 않았다.
   - 유지보수성·예외 처리: width-aware wrapping, 17행 page, clamp/reset, aria-live가 같은 row model을 쓴다.
3. 사용자 검토: 뒤쪽 내용이 존재하는지 헷갈리고 하단으로 이동할 흐름도 없어 읽기 실패가 확정적이었다. 데스크톱과 모바일 가로 모두 페이지 이동과 현재 위치를 제공하고, 측정 결과를 캐시해 긴 보고서가 답답하게 다시 배치되지 않게 했다.
4. 우선순위: P1. 화면 폭에 맞춰 줄바꿈하고 위·아래 이동, 페이지 번호, 모바일 동작명을 제공한다.
5. 실제 반영: `src/game.js`, 브라우저 테스트를 수정했다. 데스크톱 왕복, 844×390 page 2, 접근성 낭독, 전체 export 보존을 확인했다.
6. 결과: 커밋 `9df45d6`. 교사는 화면에서도 모든 행을 읽고 원본 전체 리포트도 내보낼 수 있다. 잔여 문제는 세로 화면에서는 기존 회전 안내 정책을 따르며 넓은 보고서는 가로 사용이 더 편하다는 점이다.

## 10회차 — 서비스워커 업데이트를 사용자가 안전한 시점에 적용

1. 개발자 검토: replacement `controllerchange`가 등록 뒤 60초 이내면 플레이 도중 즉시 `location.reload()`를 호출했다.
2. 코드리뷰:
   - 버그 가능성: 수업·탐험 중 배포가 진행을 끊고 프레임 사이 상태를 잃을 수 있었다.
   - 구조: 서비스워커 lifecycle이 게임 저장·화면 상태와 결합 없이 document를 교체했다.
   - 성능: 새 polling 없이 기존 30분 update check를 유지했다.
   - 보안: 같은 origin worker만 사용하며 외부 코드·권한을 추가하지 않았다.
   - 유지보수성·예외 처리: idempotent ready state, first-install 제외, explicit apply, pause save hook으로 책임을 나눴다.
3. 사용자 검토: 갑작스러운 새로고침은 진행 손실로 오해되고 수업 흐름을 끊으며, 실패 뒤 같은 장면으로 돌아온다는 보장도 없었다. 모바일·데스크톱 모두 안전 화면에서만 적용하고, 추가 polling이나 느린 강제 대기 없이 사용자가 시점을 고르게 했다.
4. 우선순위: P0. 플레이 중에는 알림만 남기고, 타이틀·일시정지에서만 native `새 버전 적용`을 보여 준다.
5. 실제 반영: `index.html`, `src/game.js`, `sw.js`, 브라우저 테스트를 수정했다. RED 4건 뒤 world 유지, hidden action, pause visible, 사용자 click 뒤 첫 navigation을 확인했다.
6. 결과: 커밋 `eb3c99f`. pause에서는 기존 save boundary를 먼저 호출하고 title에서는 빈 슬롯을 쓰지 않는다. 잔여 문제는 오래된 임베디드 브라우저에서 controller 이벤트가 누락되면 수동 새로고침이 필요할 수 있다는 점이다.

## 독립 심사 후 무결성 보완

- 코드·보안 심사에서 슬롯 key 제거가 중간에 실패할 때 일부 학습 기록만 지워질 수 있는 경계를 추가로 발견했다. 모든 대상 key의 정확한 preimage와 이전 삭제-되살리기 상태를 보존하고, 하나라도 실패하면 전체를 복구한 뒤 실패를 반환하도록 보완했다.
- 실패한 백업 가져오기가 이미 있던 복원 취소를 없애지 않도록 이전 undo를 복원한다. 내부 undo 스냅샷에는 복원 전에 없던 key도 `absent` 목록으로 남겨, 취소 시 새 key를 제거하고 정확한 이전 상태로 돌아간다.
- RED는 슬롯 중간 삭제, 기존 undo가 있는 중간 복원 실패, 없던 꾸미기 key의 복원 취소로 각각 재현했다. GREEN은 슬롯 76개와 smoke 1,216개 검사로 확인했으며 전체 브라우저·패키징·독립 심사는 최종 HEAD에서 다시 실행한다.

## 최종 결과물

- 서로 겹치지 않는 사용자 실패 경계 10개를 10개 독립 커밋으로 수정했다.
- 프레임워크·런타임 의존성·서버·로그인·API·데이터베이스·3D 자산을 추가하지 않았다.
- 메멘토형 이중 시간선, 기록 일지, 네 엔딩, 세 슬롯, 백업·복원, PWA 구조를 유지했다.
- 브라우저 회귀 검사는 개선 전 110개에서 독립 심사 보완까지 150개로 늘었다.
- 변경 파일은 기존 HTML/CSS/JavaScript와 테스트 도구, 서비스워커 캐시 버전에 한정했다.

독립 시각 검수는 첫 캡처의 잘못된 JPEG 확장자와 업데이트 버튼의 미등록 색·그림자를 차단점으로 판정했다. 시각 보정 후보에서는 DOM 디자인 토큰을 `DESIGN.md`와 같은 이름으로 연결하고, 그림자를 제거한 4px 테두리 중심 표면과 `accent-record` 포커스로 보정했다. 당시 브라우저 검사는 이 토큰 계약 2개를 추가해 147/147이 됐고, fresh update-state PNG 재검수도 통과했다. 이후 저장 무결성 심사 보완 3개를 더해 최종 브라우저 검사는 150/150이다.

## 남은 리스크

- 로컬 Playwright WebKit 바이너리가 설치되지 않아 WebKit 선택 경로는 자동 스킵된다. Chromium 실브라우저와 CI 필수 경로가 주 검증 대상이다.
- Canvas 본문은 기존 `aria-live` 미러에 의존한다. 주요 대사·알림·기록·엔딩은 미러되지만 완전한 DOM 게임은 아니다.
- localStorage 자체가 지워지거나 기기 정책으로 차단되면 서버 복구는 불가능하다. 이번 변경은 실패 경고와 로컬 백업·원자 복원을 강화한 범위다.
- 서비스워커 업데이트 버튼은 controller 상태를 브라우저 표준 이벤트에 의존한다. 오래된 임베디드 브라우저는 수동 새로고침이 필요할 수 있다.
- `src/game.js`와 `src/data.js`는 여전히 큰 단일 파일이다. 이번 출시 안정화에서는 위험한 전면 분리를 하지 않았다.
